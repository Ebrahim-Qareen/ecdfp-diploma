## 1. What the room teaches

**An insider taking data out on a USB stick, and the one structural idea worth stealing.**

🟢🟢 **Task 1 is the answer key.** Before the student touches a machine, the room publishes the
whole attack chain as an ATT&CK table — tactic, technique, and a plain-English description of what
Liam did at each step. Then Task 2 asks thirteen questions, and **every one of them is "prove that
step happened, from an artifact."**

That inverts every other room in the path, and it is a **better** assessment design than it looks:

- The student is not guessing *what* happened. They are **finding the evidence for a stated
  claim** — which is exactly what an examiner does when a hypothesis is already on the table.
- It maps directly onto **D20 criterion 3** — *"Findings — fact only, each tied to a named
  artifact."* The room supplies the claims; the student supplies the artifacts.
- 🟢 **And it makes the gaps visible.** When a step in the published chain has *no* clean artifact,
  that absence is itself the lesson — which is the D7 conversation we have been trying to
  manufacture in every other room.

**The scenario is an insider case, and the ATT&CK table is honest about what that means:** Initial
Access is **T1078 Valid Accounts** — *"Liam used his valid credentials to log into his
workstation."* **There is no compromise.** No phishing, no exploit, no malware. Everything that
follows is a legitimate user doing legitimate-looking things with illegitimate intent, and **every
artifact is a normal-use artifact.** That is a genuinely different investigation and nothing else in
the path covers it.

**🔴 But the room depends on an artifact that no longer exists on current Windows.** Question 7
asks what Liam searched for in File Explorer — which is **WordWheelQuery**, and it stopped being
written at **Windows 11 23H2**. §3 #4. **Our version cannot ask that question the same way.**

⚠️ And the scenario brief repeats room 18's mistake, harder: *"He often worked late hours without
clear justification for his extended presence. He was also caught roaming around the critical server
room and taking pictures of the entry gate."* — **behavioural prejudice presented as case
background, before a single artifact.** §4.

## 2. Artifacts — one 6-box block each

### 2.1 The USB device's serial number (`USBSTOR`)

- **What it is** — the identity of the physical stick.
- **Where it lives** — `HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR\`, as
  `<DeviceType>&Ven_<Vendor>&Prod_<Product>&Rev_<Rev>\<instance ID>`. **The instance ID is the
  serial** — Question 1's answer. ⚠️ **VID/PID are not here** — they are under
  `…\Enum\USB\`. `USBSTOR` carries the vendor/product *strings* and is **mass-storage only**.
- **What it proves** — that a device with this identity was enumerated on this machine.
  🟢 USB **mass storage is one of the few classes where a serial number is mandatory**, which is
  why USB forensics works better for sticks than for other device classes.
- **What it does NOT prove** — 🔴🔴 **that the instance ID is a serial number at all.** The
  well-known rule is: *"If the second character of the unique instance ID is a '&', then the ID was
  generated by the system, as the device did not have a serial number."*
  ⚠️ **But teach it as an indicator, not a proof.** SANS pushes back explicitly: *"We were told that
  this meant the value was generated by the computer at the time of insertion, and not from the
  factory… It turns out this is not exactly correct."* **Microsoft never documents the `&` rule** —
  it says only that *"an instance ID contains serial number information, if supported by the
  underlying bus, or some kind of location information."*
  🔴 And from the same SANS piece: *"the USBSTOR key does NOT contain all USB devices that have been
  attached."* **An absent device is not an absent connection.**
- **How to parse it** — `RECmd` over `SYSTEM`, or Registry Explorer. Timestamps live under
  `…\<instance ID>\Properties\{83da6326-97a6-4088-9453-a1923f573b29}\<NNNN>`:
  **`0064` first install (Win7+)** · **`0066` last connected (Win8+)** · **`0067` last removal
  (Win8+)**. ⚠️ **Sources disagree on whether `0064` is *InstallDate* or *FirstInstallDate*, with
  `0065` as the other — resolve by testing on our own image before labelling it on a slide.**
- **Anti-forensics / false-positive caveat** — 🟢 **serial numbers are not unique to a person.**
  The device identity ties an object to a machine; it does not tie either to a human. **§2.2 is
  where attribution actually comes from**, and running the two together is the lesson.

### 2.2 Tying the device to a user, and to a first connection

- **What it is** — the chain that turns "a stick was plugged in" into "*this user* plugged it in, at
  *this time*".
- **Where it lives** — three places, in order:
  **`HKLM\SYSTEM\MountedDevices`** — *"maps drive letters and volume GUIDs to per-device
  signatures"* (machine-wide) →
  **`HKCU\…\Explorer\MountPoints2`** — per-user, and it *"attributes the volume GUID to a specific
  user profile"* →
  **`C:\Windows\INF\setupapi.dev.log`** — the first-ever driver install, with a timestamp.
- **What it proves** — 🟢🟢 **the pivot chain**: USBSTOR serial → `MountedDevices` (drive letter +
  volume GUID) → `MountPoints2` (**which user**). And the volume GUID is what **ShellBags and LNK
  targets reference**, so this is also the join to §2.4.
- **What it does NOT prove** — 🔴 **`MountPoints2` is supporting evidence, not a device
  identifier** — a per-user key records that a volume GUID appeared in that profile, which is
  weaker than it looks when several users share a machine or a GUID is reused. ⚠️ And
  `setupapi.dev.log` records the **first driver installation**, not every connection — **a device
  used a hundred times has one entry.**
- **How to parse it** — Registry Explorer / `RECmd`; `setupapi.dev.log` is plain ANSI text with
  section headers `>>> [Device Install …]` / `>>> Section start yyyy/mm/dd hh:mm:ss.sss`.
  🔴🔴 **Those timestamps are LOCAL TIME, not UTC** — Microsoft: *"The local time is based on a
  24-hour clock."* **Every other artifact in this room is UTC on disk. Mixing them silently is how a
  timeline goes wrong**, and it is a better version of the UTC lesson than room 20's.
- **Anti-forensics / false-positive caveat** — ⚠️ the log **rotates** to
  `setupapi.dev.<YYYYMMDD-HMMSS>.log`; **collect the whole `INF` directory, not one file.**
  🟢 Also worth knowing: `HKLM\SOFTWARE\Microsoft\Windows Portable Devices\Devices` holds the
  **volume label**, which is often what a human would recognise the stick by.

### 2.3 🔴🔴 Explorer search terms — `WordWheelQuery`, and it is dead

- **What it is** — what the user typed into the File Explorer search box. Question 7:
  *"It looks like Liam searched for some files inside the file explorer. What are the names of these
  files?"*
- **Where it lives** — `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\WordWheelQuery`,
  numbered values holding one **UTF-16LE** term each, with **`MRUListEx`** giving the order
  (4-byte little-endian indices, most recent first).
- **What it proves** — 🟢 **intent, in the user's own words.** A search for a filename is a
  statement about what someone was looking for, and it survives even when the file does not.
- **What it does NOT prove** — 🔴🔴 **and this is the finding that matters: on Windows 11 23H2 and
  later, the key is no longer populated at all.** A SANS instructor's observation, published
  Oct 2024: *"in Windows 11 23H2 the WordWheelQuery value is no longer populated"*, because
  *"searches are basically conducted as you type rather than on pressing enter"* and the shell now
  queries the search index directly. **13cubed's Registry Cheat Sheet v2.0 now carries the version
  bound explicitly: *"Explorer search history (Windows 11 22H2 / Server 2022 and earlier)."***
  ⚠️ **So an empty `WordWheelQuery` on a modern host means nothing.** It is not "the user did not
  search" and it is not "the user cleared it" — **the artifact simply is not written any more.**
- **How to parse it** — `RECmd` over `NTUSER.DAT`; decode `MRUListEx` for order.
  🟢 **The successor is `HKCU\…\Explorer\TypedPaths`**, which records the search as a `search-ms:`
  URI including the term and the folder it was run against — ⚠️ **but `TypedPaths` holds only ONE
  timestamp for the whole key, so you cannot date an individual search.**
- **Anti-forensics / false-positive caveat** — 🟢🟢 **this is now our best "the artifact changed
  under you" case, and it is worth more than the artifact was.** The lesson is not
  *"check WordWheelQuery"*; it is **"know the OS version before you interpret an absence"** — and
  the same page of the same cheat sheet that taught this key now dates it. **Put the two versions of
  the cheat sheet side by side on a slide.**

### 2.4 ShellBags — the structure of a drive that is no longer there

- **What it is** — folder navigation history, including for **removable media**. Question 8:
  *"What are the names of the folders that were present on the USB device?"*
- **Where it lives** — `USRCLASS.DAT\Local Settings\Software\Microsoft\Windows\Shell\` →
  **`BagMRU`** (the tree) and **`Bags`** (the view settings).
- **What it proves** — 🟢🟢 **the folder structure of a drive that was disconnected, wiped or
  destroyed**, attributed to a specific user by virtue of the hive it lives in, with the folder
  timestamps from when it was first browsed. **This is the only artifact that answers Question 8 at
  all**, and it is the strongest argument in the course for why ShellBags matter.
- **What it does NOT prove** — 🔴 **three things, and Cyber Triage states all three:**
  1. **Not that the user opened *that* folder** — *"parent folders are logged even without direct
     access."* Navigating to `E:\Work\Q3` creates entries for `E:\` and `E:\Work` too.
  2. **Not a successful access** — *"denied access attempts still create entries without view
     preferences."*
  3. **Not file access** — *"only folders are recorded."* **A ShellBag never tells you a file was
     opened.**
  🟢 The presence of *applied view preferences* is the discriminator between a folder that was
  merely traversed and one the user actually worked in.
- **How to parse it** — **ShellBags Explorer / `SBECmd`, both `2026.5.0`.** ⚠️ **Eric Zimmerman's
  GUI tools are now .NET 9 only** — *"Legacy net4 versions are no longer available"* — which is a
  lab-build requirement, not a footnote.
- **Anti-forensics / false-positive caveat** — 🟢 **cross-reference the volume GUID** from §2.2 to
  prove the ShellBag belongs to *this* USB device rather than another removable drive. **Two
  artifacts, one join — that is a corroborated finding rather than an assumption.**

### 2.5 Execution count and last-run time (Prefetch)

- **What it is** — proof that `file_uploader.exe` ran, how often, and when last. Question 9 asks for
  **both** — *"When was this file last executed and how many times was it executed?"*
- **Where it lives** — `C:\Windows\Prefetch\<NAME>-<HASH>.pf`.
- **What it proves** — 🟢 **run count and up to eight execution timestamps** — which makes it the
  only artifact in the room that distinguishes *"it ran once"* from *"it ran repeatedly"*.
  🟢 **And the room asks for both fields, which is good question design**: a run count is a
  different claim from a last-run time and students routinely conflate them.
- **What it does NOT prove** — 🔴 **that it succeeded, or what it did.** The room's ATT&CK table
  says `file_uploader.exe` was *"responsible for uploading any future data in the Documents
  folder"* — **prefetch proves execution, nothing more.** ⚠️ And prefetch is **disabled by default
  on Windows Server**, and can be disabled on workstations; **absence is a configuration question
  before it is an evidence question.** ⚠️ The eight-timestamp limit means a frequently-run binary
  loses its early history.
- **How to parse it** — `PECmd`. Corroborate with **Amcache** (presence + SHA-1) and be careful with
  **ShimCache** (presence and enumeration, **not** execution).
- **Anti-forensics / false-positive caveat** — 🟢 **prefetch also lists the files the binary
  touched**, which for an uploader is the closest thing to a target list you will get from the
  endpoint. **The room does not ask for it. We would.**

### 2.6 The Recycle Bin — `$I` metadata files

- **What it is** — the record of a deletion that went through the Recycle Bin. Question 11:
  *"When did Liam delete 'Tax Records.docx'?"*
- **Where it lives** — `C:\$Recycle.Bin\<SID>\`, one subdirectory per user **named by SID** (which
  is the attribution), with **`$I<random>`** holding the metadata and **`$R<random>`** the content.
- **What it proves** — original path, original size, and **the deletion timestamp as a FILETIME**.
  **Windows 10/11 `$I` format (version 2):**

  | offset | bytes | field |
  |---|---|---|
  | 0 | 8 | version code — **`02`** |
  | 8 | 8 | original file size |
  | 16 | 8 | **deletion timestamp (FILETIME)** |
  | 24 | 4 | **length of the original path** |
  | 28 | *n* | original path, UTF-16LE |

  ⚠️ **Vista–8.1 used version `01`, a fixed 544 bytes with a 520-byte path field** (520 = 260 chars
  × 2 = MAX_PATH). **The 4-byte length field at offset 24 is what makes v2 variable-length**, and
  it is the thing to point at when explaining why old parsers break.
- **What it does NOT prove** — 🔴 **that the file is gone, or that the user emptied the bin.**
  A `$I` without its `$R` means the bin was emptied; a `$I` *with* its `$R` means the file is still
  recoverable. ⚠️ **And a Shift+Delete never touches the Recycle Bin at all** — that deletion has
  no `$I` and must be proved elsewhere (§below). ⚠️ Nor does it prove *who* pressed delete, only
  which profile's bin it landed in.
- **How to parse it** — **`RBCmd`, version `2026.5.0`**.
- **Anti-forensics / false-positive caveat** — 🟢🟢 **when the bin has been emptied, `$UsnJrnl:$J`
  is the answer**, and the signature is a *sequence*, not an event. Microsoft: a rename generates
  **two** records — `USN_REASON_RENAME_OLD_NAME (0x1000)` and `USN_REASON_RENAME_NEW_NAME
  (0x2000)` — *"and when a file or directory closes, a final USN record is generated with the
  `USN_REASON_CLOSE` flag set."* So **recycle-then-empty reads as: rename into `$Recycle.Bin`
  (old/new name pair) → `USN_REASON_FILE_DELETE (0x200)` | `CLOSE (0x80000000)`.**
  **Teach the sequence — it survives the emptying, and it distinguishes a recycle from a
  Shift+Delete.**

### 2.7 Document metadata and file signatures

- **What it is** — two questions, one principle. Question 5: *"who is the author of the PDF file
  stored in the zip?"* Question 6: *"what is the correct extension of the file that has no
  extension?"*
- **Where it lives** — for the PDF, **two independent places**: the **DocInfo dictionary
  (`/Author`)** and the **XMP metadata stream (`dc:creator`)**. For the extensionless file, the
  **magic bytes** at the head of the file.
- **What it proves** — the name a document claims for its author, and the format a file actually is.
- **What it does NOT prove** — 🔴🔴 **for the PDF: that the author field is true, and — the better
  lesson — the two locations can disagree.** The PDF/A specification requires that where both exist
  they *"must match… on a character-by-character basis"*, but **nothing says which wins when they do
  not.** 🟢 **A mismatch is itself the finding**: it indicates the document was edited by a writer
  unaware of the XMP stream. **Report both values and the discrepancy. Never silently pick one.**
  ⚠️ For the extensionless file: **magic bytes are spoofable too**, though asymmetrically —
  *"changing file extensions is a very convenient and easy way"* to hide something, whereas
  *"affecting the signature… alters the internal structure of the file and makes it not readable
  anymore."* **Signature analysis is robust against extension spoofing and not against a determined
  header edit.**
- **How to parse it** — **ExifTool 13.59 (May 2026)** for both PDF metadata sets. For file typing,
  `file` is *"clearly the quickest solution with good performance"*; **TrID** has by far the largest
  signature database; a 2023 peer-reviewed comparison of ten tools found *"significant disparity in
  accuracy and behavior"* — **do not teach one tool as authoritative.**
- **Anti-forensics / false-positive caveat** — ⚠️ shared headers, truncation, and packed or
  encrypted files all defeat signature analysis. **Layer it**: signature + hash + metadata +
  entropy. 🟢 And note the room's Question 6 has exactly one defensible answer only because the
  file is intact — **on a carved fragment it would not.**

### 2.8 The personal hotspot

- **What it is** — Question 2: *"the profile name of the personal hotspot Liam used to evade
  network-level detection."* **An insider stepping off the corporate network to exfiltrate.**
- **Where it lives** — the WLAN profile store (`C:\ProgramData\Microsoft\Wlansvc\Profiles\
  Interfaces\{GUID}\*.xml`) and the network list registry keys
  (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\NetworkList\{Profiles,Signatures}`).
  ⚠️ **Exact key layout and value semantics NOT VERIFIED this pass — confirm before teaching.**
- **What it proves** — 🟢🟢 **a deliberate act with no innocent reading.** A corporate workstation
  associating with a phone hotspot, at the same time as an exfiltration binary runs, is the single
  most damning artifact in the room — **because it is a choice, not a side-effect.**
- **What it does NOT prove** — 🔴 **that data went over it.** A stored profile proves the network
  was configured and, with the NetworkList timestamps, that it was connected. **It does not prove
  what traversed it** — the room's ATT&CK table asserts exfiltration; the WLAN artifact corroborates
  *opportunity*. ⚠️ And a profile can be created and never used.
- **How to parse it** — read the profile XML (it carries the SSID and, ⚠️ **often the pre-shared key
  in an encrypted `keyMaterial` element — R8: do not reproduce it in a report body**); pair with
  NetworkList for first/last connected.
- **Anti-forensics / false-positive caveat** — 🟢 **this is the artifact that makes the case an
  insider case.** An external attacker does not need to bring their own network. **Ask students what
  the presence of a hotspot profile means that a VPN client would not.**

## 5. Lab design worth reusing

1. **🟢🟢 Publish the attack chain up front and make the student prove each step.** Task 1 is an
   ATT&CK table with plain-English activity descriptions; Task 2 asks for the artifacts.
   **This is the single best assessment idea in twenty-one rooms** and it maps straight onto **D20
   criterion 3**. 🟢 **And it makes gaps visible**: a published step with no clean artifact is the
   D7 conversation, pre-built.
2. **🟢🟢 An insider case with `T1078 Valid Accounts` as initial access.** No compromise, no
   malware, **every artifact a normal-use artifact.** A genuinely different investigation, and the
   one our students are most likely to actually run.
3. **🟢 Ask for two fields from one artifact.** Question 9 wants *last executed* **and** *how many
   times* — different claims from the same file, and students conflate them.
4. **🟢 Alphabetical-order answers** for multi-value questions (Q7, Q8). Removes ordering ambiguity
   without making the question easier. **Copy this.**
5. **🟢 A hotspot as the exfil path.** The artifact that makes an insider case an insider case
   (§2.8), and no other room in the path has it.
6. **🟢 Give the student a pre-ingested case with the image present.** Cheaper than a full
   acquisition exercise, and unlike room 16 the evidence is actually readable.
7. **🔴 Do NOT reuse the character evidence in the brief** (§4) — **use it as an exercise instead.**
8. **🔴 Do NOT ask for the zip password as an answer** (Q4) — same handling problem as room 20 §2.8.
   **R8: the finding is that the password was in the PDF, not the password.**

## 6. Question patterns

**13 questions, one task, no scaffolding — and the design is deliberate.**

**🟢🟢 The set covers eleven distinct artifacts and never asks the same one twice.** USB registry ·
WLAN profiles · archive contents · document metadata · file signature · Explorer search ·
ShellBags · prefetch · hidden data · Recycle Bin · browser history · PowerShell history.
**That breadth is what makes it a capstone rather than a quiz**, and it is a better artifact
inventory than our own S4/S5 rows currently cover.

**🟢 Answer formats are specified** — `YYYY-MM-DD HH:MM:SS`, *"alphabetical order"*, *"Full URL"*,
*"number of execution times"*. Same discipline as rooms 19 and 20; same contrast with room 18.

**🟢 Question 9 asks for two fields from one artifact** (§5.3).

**⚠️ But nearly every stem asserts its own conclusion** — *"the USB device Liam used **for
exfiltration**"* · *"the hotspot Liam used **to evade network-level detection**"* · *"the zip file
Liam copied from the USB **for exfiltration instructions**"* · *"Liam **caused one last damage**
before leaving"* · *"**Likely to avoid suspicion, thinking somebody was watching him**"*.
🔴 **That last one is not even a conclusion about the evidence — it is a conclusion about Liam's
state of mind, in a question stem.** The published attack chain (§5.1) makes some of this defensible
— the student is proving stated claims — **but a stem should still say what to find, not why it
happened.**

**🔴 Twenty-first room, no "cannot be determined" question** — and this room's artifact set makes
the omission unusually sharp, because **six of its thirteen artifacts have a well-known limit that
the question ignores:**

| the room could have asked | correct answer |
|---|---|
| *"The instance ID is `7&d2713f&0`. What is the device's serial number?"* | 🟢 **There is none** — the second character is `&`, so Windows generated the ID. ⚠️ And even that is an indicator, not a proof. |
| *"ShellBags show `E:\Exfil\`. Did Liam open that folder?"* | **Not established** — *"parent folders are logged even without direct access"*, and a denied access still creates an entry. |
| *"`WordWheelQuery` is empty. Did Liam search for anything?"* | 🔴🔴 **Cannot be determined — on Windows 11 23H2+ the key is not written at all.** §3 #4. **The best question in this table, and the room cannot ask it because it does not know.** |
| *"Prefetch shows 4 executions. Did the uploader succeed?"* | **No** — prefetch proves execution. Success needs network evidence. |
| *"The `$I` file gives a deletion time. Is that when the file was destroyed?"* | **No** — it is when it went to the bin. Destruction is the *emptying*, and that is a `$UsnJrnl` sequence. |
| *"The PDF author is 'X'. Who wrote it?"* | **Unknown** — and **check `dc:creator` against `/Author`; a mismatch means it was edited.** |
| *"A hotspot profile exists. Did data leave over it?"* | **Not proven** — a profile proves configuration and, with NetworkList, connection. Not traffic. |

🟢🟢 **Seven, and the third one is a question the room's own authors could not have written**,
because it depends on a currency finding published after the room was built. **That is the clearest
possible argument for why every artifact lesson needs a version bound attached to it.**
