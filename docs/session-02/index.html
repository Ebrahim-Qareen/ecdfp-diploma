Session 2

Acquisition: Disk, Memory & Live Response

By the end of today you can walk up to a running machine, collect what is about to disappear, image what is left, and prove exactly what you did and what your proof does not cover.

Recap — Session 1

You verified a set of files against a signed manifest, found the one that had been altered, and wrote it up as a finding rather than a conclusion. You closed a custody line and signed it.

Session 1's closing sentence is today's opening question: “Everything you just did was preparation. Nothing has been acquired yet.”

And the thing worth noticing first

Session 2 is where the evidence is created. Every artifact you examine in Sessions 3 to 6 comes out of the images you make today. An analysis error can be corrected by running the tool again. An acquisition error cannot be corrected at all.

How this session works

Three kinds of statement, and one new habit

Everything you write is still graded on keeping these apart. Colour is never the only signal — the border style carries the same meaning, so the distinction survives a bad projector and a greyscale printout.

Finding

The acquisition log records the image hash as <value> and the read-back verification as verified.

Interpretation

The image was written without a read error, so the copy is faithful to what was read.

Cannot prove

Whether the source drive was altered before it reached the examiner. Verification never re-reads the source.

New today: a micro-lab after every block

You watch it once, then you do it yourself, then you check it against one line. Eight times.

  1. WATCH — one command or one action, demonstrated
  2. DO — the same thing, on your own machine
  3. CHECK — one line you compare against: pass or fail
  4. WHY — what it proves, and what it does not

S2-01 · 8 min

You learned the list. Now start the clock

In Session 1 the order of volatility was a ladder to recite. Today it is a race you are losing while you work. Collection is not free: every minute you spend on one store, the stores above it keep decaying.

S2-F1 — press play, then click any highlighted part of the figure

Press play: while the collection job moves down the list, everything above it is still decaying.

RAM — collect it first or lose it

Gone completely on power loss. It holds running processes, open connections, injected code and anything decrypted only in memory.

Start lower and you lose: every one of those, permanently. There is no partial recovery.

Network state — the fastest to rot

Connections, ARP cache and routing change second by second, and they keep changing while you capture memory.

Start lower and you lose: the live picture of what the host was talking to. The pcap and the memory image can partly rebuild it — partly.

Running processes — gone at reboot

The process list, loaded DLLs and open handles survive only while the machine runs.

Start lower and you lose: what was executing. Disk artifacts show what could run, never what was running.

Disk — the one that waits for you

Survives power loss. This is why it is imaged last, not first.

The Case 01 error: the responder went straight here by powering the host down. Everything above this bar was destroyed before the examiner arrived.

Cannot prove

What was in RAM on a host that was powered down before you arrived. There is no partial recovery and no later technique that reaches it.

You arrive at a running host and begin by imaging the disk. What is already gone by the time you finish?

S2-02 · 13 min

To preserve a running machine, you must change it

Live response is collecting volatile data from a host that is still running. There is a paradox at the centre of it: every command you run changes the machine you are trying to preserve. There is no clean option. There is only a recorded one.

And there is a second problem. A collector asks the operating system what is running. If the operating system has been subverted, it answers with the list the attacker wants you to see.

S2-F2 — press play, then click any highlighted part of the figure

The report is not wrong about what it saw. It is wrong about what there was to see.

The report — accurate, and incomplete

The collector asked the operating system for the process list and wrote down the answer. Every line in it is real.

The problem is what is missing. A collector cannot report a process the operating system declines to mention.

The three the report never showed

If the operating system has been subverted, it answers the query with the list the attacker wants you to see.

This is why a clean live-response report is not evidence that the host is clean. It is evidence of what the host said about itself.

The artifact that would catch it

The memory image. pslist walks the same structures the operating system uses, so it inherits the same lie. psscan scans memory for process objects directly.

Run both and diff them. That is Session 6 — and it only works if you captured memory today.

A live-response collector returns a completely normal process list. What does that establish?

S2-02 · 12 min · micro-lab

What a collection run leaves behind

Two of the four things in this tree are a record of the host. The other two are a record of your own conduct, and they are the ones that make the collection defensible.

S2-F3 — click any highlighted part of the figure

Two of these four files are the record of your own conduct, not of the host.

ForensicImages\Memory\

Holds: the raw memory capture — roughly the size of physical RAM.

Cannot tell you: the state at a single instant. The capture is a smear across the window between its start and finish times.

LiveResponseData\

Holds: process list, DLLs and handles; connections, ARP, routing, DNS cache; logged-on users; uptime, patches, services, scheduled tasks.

Cannot tell you: anything the operating system chose not to report. Everything here came through the OS API.

The per-file hash list

Proves: the collected files have not changed since collection.

Does not prove: that the collection itself was complete or truthful. Check the row count against the number of files — a missing row means a file was collected without being hashed.

Processing_Details.txt — the important one

Holds: every command you ran, with its start and finish time.

ISO/IEC 27037 requires that a qualified third party can reconstruct what you did. On a live host that is only possible if this file was written as you worked. Reconstructed afterwards, it is a story, not a record.

S2-03 · 12 min

Why memory comes first, and why it is never a snapshot

Memory holds what exists nowhere else: running processes, open connections, injected code, loaded drivers, and data that is only ever decrypted in RAM. Power off and it is gone.

But the capture is not instantaneous. The tool reads from low addresses to high and takes minutes, and the machine keeps running the whole time.

S2-F4 — press play, then click any highlighted part of the figure

The top of the dump and the bottom were read minutes apart, and the machine did not wait.

The top — read first

Low addresses are read at the start. What is recorded here is the state at t + 0, not at the moment the capture finished.

The process that exits mid-capture

Process B was alive when the head was above it and gone before the head reached its pages. Depending on where its structures live, the dump may hold it, may hold a fragment, or may miss it entirely.

This is why a page-level consistency claim cannot be made.

The bottom — read last

High addresses are read minutes later, and process D did not exist when the capture began.

Two structures in the same dump can legitimately disagree with each other. That is not corruption — it is the smear.

What it makes unreliable, and what it does not

Unreliable: any claim that two structures were consistent with each other at one instant; counts that must add up exactly.

Unaffected: an artifact you actually find. Strings, injected code and connections recovered from the dump were really there. The correct sentence is “present during the capture window”, and you state the window.

Finding

The memory capture of FIN-WKS-07 ran from 14:12 to 14:19 UTC and produced a 16 GiB image.

Interpretation

The process observed in the image was present at some point during that window.

Two structures in the same memory image disagree with each other. What is the most likely explanation?

S2-03 · 8 min · micro-lab

Four things that stop you, and what you write when they do

S2-F5 — click any highlighted part of the figure

None of these are reasons to write nothing down.

Driver signing enforcement

Windows refuses to load an unsigned kernel driver, and most capture tools need one. The tool reports a driver load failure, not a memory error.

Way round: use a tool whose driver is signed. Record which tool and version you used and why.

Secure Boot

The block happens below the operating system, so no amount of local administrator rights helps.

Way round: a signed tool, or accept it and write the limitation: “memory capture attempted at 14:05 UTC and refused by Secure Boot”. That sentence is defensible; silence is not.

A hypervisor

Inside a guest you can only capture the guest’s own memory. The hypervisor’s memory, and every other guest, is invisible.

Way round: capture at the host, or suspend the VM and take its memory file — which is often cleaner than a live capture, because the guest is frozen and there is no smear.

An anti-cheat or EDR driver

Security drivers actively defend the kernel against exactly the technique a memory acquisition tool uses. Best case the tool is blocked; worst case the host bugchecks — and then you have lost the memory anyway.

Way round: coordinate with the vendor before you try. Record the attempt and the refusal either way.

S2-04 · 12 min

One disk, two envelopes

A physical acquisition takes every sector on the device. A logical acquisition takes the files the file system chooses to show you. The gap between them is not a technicality — it is where Session 4 does its work.

S2-F6 — click any highlighted part of the figure

The gap between the two brackets is the evidence Session 4 needs.

Allocated files — both reach this

The files the file system currently lists. Physical and logical acquisition both capture them, with their metadata.

If this were all a case ever needed, logical acquisition would be enough. It almost never is.

Slack space — physical only

The unused remainder of the last cluster of a file. It holds whatever was there before, and the file system does not present it as data at all.

Lost by a logical acquisition.

Unallocated space — physical only

Clusters not currently assigned to a file: deleted files, deleted staging archives, remnants of anti-forensic clean-up.

Session 4 recovers the deleted staging files from exactly here. Take a logical image today and Session 4 has nothing to work on.

HPA / DCO — physical, and only if you ask for it

Host Protected Area and Device Configuration Overlay are regions the drive can be told to hide from the operating system.

A physical acquisition reaches them if the imaging path does not honour the hiding. Record whether your tool and blocker did — it is a real limitation to state.

The acquisition decision made today sets the ceiling on every later session.

Which later session is made impossible by taking a logical image today?

S2-04 · 8 min · micro-lab

Four ways to take it, three of them narrower

S2-F7 — click any highlighted part of the figure

Every method except the first is a decision to collect less, and it has to be recorded as one.

Disk-to-image — the default

Produces one or more image files from the source device, with compression and metadata if the format supports it.

Right when: you can take the whole device. This is what you do unless a stated reason stops you.

Disk-to-disk (clone)

Writes the source sector for sector onto a second physical disk.

Right when: the destination must boot or be read by original hardware. Forfeits: compression, case metadata and an embedded hash — and you need a disk at least as large as the source.

Sparse acquisition

Captures selected portions of the device only.

Right when: legal scope is genuinely narrow and the boundary is defensible. Forfeits: everything outside the selection — and you cannot later show what was there.

Logical acquisition

Captures selected files as the file system presents them, in a container.

Right when: the device is enormous, or encrypted at rest and only readable while unlocked. Forfeits: slack, unallocated space and every deleted file — which caps Sessions 4 and 5.

Micro-lab 4 — image the same volume twice

DO: image your 100 MB scratch volume physically, then logically.

Verification line

Finding

S2-05 · 8 min

What is actually inside the container

Three formats, and only one of them carries a way to check itself.

S2-F8 — click any highlighted part of the figure

Only one of the three carries a way to check itself.

E01 — what its verification actually verifies

The container holds case metadata, the data in segments with a CRC on every chunk, and an image hash computed at acquisition.

Verification proves: the image is internally intact and matches the hash written when it was made. It does not re-read the source device, so it says nothing about whether the image still matches the original drive.

raw (dd) — nothing to verify against

A byte-for-byte copy with no header, no metadata and no hash inside it.

Verification proves: nothing on its own. Its integrity depends entirely on a manifest you compute and keep separately — which is exactly why dc3dd’s hash= and log= matter.

Why keep it: every tool on earth reads it.

AD1 — a logical container

Holds selected files only, with a container hash.

Verification proves: the selected files are intact. It cannot prove anything about data that was never selected — there is no unallocated space in an AD1.

⚠️ Autopsy cannot open AD1. Match the format to the tool before you acquire, not after.

You will analyse this image in Autopsy. Which format do you not acquire to?

E01's embedded hash verifies the image against itself. It never re-reads the source.

S2-06 · 10 min

The most important sentence in the session

FTK Imager 8.3 finishes, and the log says verified. Almost every student reads that as the evidence is untampered. It does not mean that, and the difference is examinable.

S2-F9 — press play, then click any highlighted part of the figure

The loop closes on the right-hand side of the picture, and the source drive is never touched again.

The source drive — read once

The imaging tool reads the source once, while writing the image. After that it is never read again during verification.

So the verification result carries no information about the source’s state at any later moment, and none at all about its history before you arrived.

Digest A — computed while writing

As the tool writes the image it hashes the data going past. That is digest A, and it is what appears at the top of the log.

Digest B — the read-back

With Verify images after they are created ticked, the tool reads the finished image back off disk and hashes it again.

If A equals B, the write was clean: nothing was corrupted between memory and storage. That is a real and useful guarantee — it is simply a narrower one than students assume.

The sentence you may write, and the one you may not

May write: F-02 — The acquisition log records the image hash as <value> and the read-back verification as verified (FTK Imager 8.3).

May not write: the image is verified, so the disk was not tampered with.

Verification covers the copy. The history of the original is the chain of custody’s job, and that is paperwork, not a digest.

You may write

  • the acquisition log records the image hash as <value>
  • the read-back verification returned verified
  • the image was written without a read error
  • the tool and version were FTK Imager 8.3

You may not write

  • the image is verified, so the disk was not tampered with
  • the source drive is unaltered
  • the evidence is authentic
  • nothing was changed before seizure

The log says verified. Which comparison did the tool never make?

S2-07 · 8 min

Three tools, three jobs

S2-F10 — click any highlighted part of the figure

The image bytes are the same. What differs is what you can prove about them afterwards.

dd — the one command, and its catch

sudo dd if=/dev/sdX of=/evidence/out.dd bs=4M

The catch: no hash and no log. You must hash the source and the image yourself in separate steps and record them by hand — and if the two disagree, nothing tells you where the read failed.

dc3dd — the one command, and its catch

sudo dc3dd if=/dev/sdX of=/evidence/out.dd hash=sha256 log=/evidence/out.log

The catch: it is dormant software — maintained rarely, not dead. Version-bind it (7.3.1 here) and say so, rather than pretending it is actively developed.

KAPE — the one command, and its catch

kape.exe --tsource C: --tdest E:\triage --target !SANS_Triage

The catch is the licence, and it is not technical. KAPE is no longer available for commercial use as of 1 January 2026 — on a third-party network or as part of a paid engagement. Classroom use is educational and remains free.

Pair every KAPE step with the free path: the EZ Tools underneath are separately free, and a target set is only a list of file paths a script can collect.

S2-F11 — click any highlighted part of the figure

Triage trades completeness for speed, and the trade has to be written down.

What a triage target set collects

Registry hives, event logs, prefetch, $MFT, jump lists, browser history — the artifacts that answer the common questions quickly.

It is fast, it is small enough to move over a network, and it does not require taking the host offline. Those are real advantages.

What it leaves behind

Unallocated space, file slack, deleted files, and anything not named in the target list.

The target list is a decision about what the case will be allowed to ask. Record which target set you used and its version — “I ran a triage collection” is not reproducible.

The question you can no longer answer

A deleted archive lives in unallocated space. A triage set never collected it, so the question cannot be answered later — not by re-examining the set, and not by any tool.

You cannot go back for it unless the original device is still available and unaltered. Usually it is not.

The USB device seized from FIN-WKS-07 is a separate exhibit. Nothing about its contents has been established. Your job in this case is acquisition and verification only.

S2-F13 — press play, then click any highlighted part of the figure

Four questions, four written answers. The decision is part of the evidence.

Is the host running?

Yes: capture volatile data first — live response, then memory — then power down and image. No: do not power it on. Image the disk as it is.

Powering on a seized machine writes to it: services start, logs are written, timestamps move. It is one of the few actions that cannot be undone or explained away.

Is the data encrypted at rest?

If the volume is encrypted, a powered-down image may be unreadable no matter how perfect the acquisition.

Capture while the volume is unlocked, or capture the key material in memory — which is another reason memory comes first. Record which you did.

Is time short, or the device too large?

Then triage is on the table — but it is a decision to collect less, and you record exactly what you chose not to collect.

“There was not time” is an acceptable reason. Not writing it down is not.

Which method

Physical, disk-to-image, is the default. Anything narrower is a deliberate choice with a stated reason.

This is the step external labs skip entirely: they hand you a device and tell you to image it. Deciding how, and defending the decision, is the part that is examined.

Before you image anything

Work down the decision path and write your answer at each step. The four answers are part of the deliverable — the decision is evidence.

fact only, tied to one named artifact at an exact path

I-01

what it means, with its basis, clearly separated

L-01

what this evidence cannot show, however it is read

Two sentences will cost you marks: “the USB was used to steal data” and “verified, so it was not tampered with.”

Q6 is answerable only as a limitation

The structure shows that space is unaccounted for. It cannot show why. A correct answer says so and stops — an unallocated gap has several innocent explanations and the image distinguishes none of them.

Give offsets and sizes as numbers, not descriptions. “A small gap near the end” is not reproducible.

Summary

Takeaways

  1. verified means the tool checked its own output. It never re-read the source, so it says nothing about the original's history.
  2. Collection is a race. Every minute spent on one store, the stores above it keep decaying. The order is a decision about what you accept losing.
  3. A memory capture is a smear, not a snapshot. State the window, not an instant.
  4. The acquisition decision sets the ceiling on every later session. A logical image today ends Session 4 before it starts.
  5. A failed capture, and anything you chose not to collect, are findings. Write them down. Silence is the only unrecoverable error.
