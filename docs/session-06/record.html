Chain-of-Custody Record

Session 06 Examination · Analysis · Presentation

One unbroken record for the case. Tick each step as you do it, open example for a correct entry, what to record and why it matters, then write your own entry. Saves in this browser and carries forward into later sessions. Export to HTML or PDF — the exported file is what you submit.

Standards. Structure follows SWGDE 18-Q-002 (report content), SWGDE 18-F-002 (evidence collection and custody) and ISO/IEC 27037 (identification, collection, acquisition, preservation). The governing rule: every action must be reconstructible by a qualified third party. Evidence IDs come from the case manifest (EVS-02 · EVS-03 · EVS-08); digests in examples are placeholders. The browser copy is a working copy — the exported file is the record of authority.

B · Receipt & integrity

Exhibit receipt & identificationloglog the package before you open it
Example
EVS-01 — received
# 6 files, as distributedseizure_notes.txt · EVI-SRC01_acquisition_log.txtcustody_form_EVI-SRC01.txt · evidence_inventory.csvEVS-01.sha256 · EVS-01.md5 # the signed manifestreceived: instructor distribution · state: read-only, complete
Record
  • Unique identifier and description of the item (SWGDE §5.3)
  • Date and time of receipt, and from whom
  • Delivery method, and its state as received — complete, read-only
  • Where it is stored and how access is controlled
Why it matters · admissibility: SWGDE 18-Q-002 §5.3 requires each item to be uniquely identifiable — by make, model, serial number or hash. A vague head of chain means nothing below it ties to a specific item.
Integrity verification against the signed manifestactivesha256sum -c EVS-01.sha256
Example
verify against the manifest
$ sha256sum -c manifest.sha256exhibit_A.txt: OKexhibit_B.txt: OKexhibit_C.txt: FAILEDsha256sum: WARNING: 1 computed checksum did NOT match
Illustrative names — which file fails in EVS-01 is yours to find.
Finding — how to write it

exhibit_C.txt did not verify: computed SHA-256 <digest> ≠ manifest <digest>. Both algorithms recorded.

Record
  • Tool and version — e.g. sha256sum (GNU coreutils 9.4)
  • MD5 and SHA-256 per file — both, every time
  • Result per file: match or mismatch — a mismatch is recorded, never omitted
  • The two digests being compared for any file that failed
Why it matters · admissibility: SHA-256 is the value you defend; MD5 is a lookup key, never the control. A mismatch is a finding, not an inconvenience — and a tool reporting “verified” means it compared its own write to its own read-back, not that the evidence is untampered.
Working copy & write-block disciplineactiveexamine the copy, never the original
Example
work on a copy · prove read-only
$ cp -r EVS-01 EVS-01_working$ (cd EVS-01_working && sha256sum -c EVS-01.sha256)# imaging a device instead? record the blocker BEFORE connecting the source:Write blocker: Tableau T8u · engaged <time> UTC · verified read-only
Record
  • Working-copy path and its hash — equal to the original's
  • Confirmation the original was not worked on
  • For a device: write-blocker make/model, engaged before the source was connected
  • For a read-only file set: that no blocker was required — and say so explicitly
Why it matters · admissibility: Proves the original was never altered. Recording how read-only was assured is what answers the challenge “how do you know you didn't change it?” — the question every cross-examination reaches eventually.

B · Identification & collection

Scene & device documentationlogdocument before you touch
Example
device as found
Statepowered ON · screen unlocked · 2 windows openMake / model<make> <model>Serial<serial>Conditionno damage · 1 USB device attachedLocation<where> · photographed
Record
  • Device state — powered on or off, screen locked, open files or windows
  • Physical characteristics — make, model, serial, damage, identifying marks
  • Every connection and attached device
  • Location, described in writing and photographed
Why it matters · admissibility: SWGDE 18-F-002 requires all of this at collection. Powered off, you do not turn it on; powered on, you never reboot. The state as found can only be recorded once — and it is the fact a later examiner cannot recover.
Volatile capture — order of volatilityactiveRAM before disk · isolate the network
Example
volatile first
# most volatile first: RAM → connections → processes → disk> winpmem_<ver>.exe -o E:\mem.rawacquired 16 GiB · SHA-256 <digest># network isolated before collection · least-invasive tooling
Record
  • Order of collection actually followed, most volatile first
  • Memory tool and version, dump size, and its hash
  • That the host was isolated from the network, and when
  • Every command run on the live host — each one changes it
Why it matters · admissibility: Volatile data is destroyed by the next action, including yours. ISO/IEC 27037 asks that a third party can reconstruct what you did; on a live host that is only possible if every command and its time are recorded as you go.

C · Acquisition & imaging

Write blocker engagedactiverecord it BEFORE connecting the source
Example
write blocker
TypehardwareMake / modelTableau T8uEngaged<YYYY-MM-DD hh:mm> UTC — before connectionVerifiedread-only confirmed
Record
  • Hardware or software blocker, with make/model or product and version
  • The time it was engaged — which must precede connecting the source
  • How read-only was verified
Why it matters · admissibility: The blocker is only evidence of anything if it was recorded before the source was attached. Written afterwards it proves nothing, because the write you are ruling out would already have happened.
Image acquisitionactiveFTK Imager 8.3 · dc3dd
Example
acquisition log
ToolFTK Imager 8.3Source<device> · <serial>Destination<path>/EVI-SRC01.E01FormatE01 · segment 2048 MB · compression 6Sectors<n> · errors: 0
Record
  • Tool and exact version — a tool without a version is not a method
  • Source device and destination path
  • Format and why: E01 (embedded verification) vs raw/dd vs AFF4, and segment size
  • Sectors imaged and any read errors — errors are recorded, not hidden
Why it matters · admissibility: This is the acquisition ISO/IEC 27037 means: a verifiable bit-stream copy. The reader has to be able to repeat it on the same build and reach the same image, which is only possible if the tool, version and settings are on the record.
Acquisition & verification hashactiveacquisition hash must equal verification hash
Example
FTK Imager — verify results
[Computed Hashes]MD5 <digest>SHA-256 <digest>[Verify Results]Verify result: Match
Record
  • Hash at acquisition, MD5 and SHA-256
  • Hash re-computed at verification, and the result: match or mismatch
  • The verification was of the image against the source, and it says so
Why it matters · admissibility: The pair is the point: one hash proves nothing, two equal hashes prove the copy is faithful. A mismatch is recorded and explained — an unexplained mismatch ends the evidential value of the image.

File signature versus extensionactiveheader / magic bytes, not the name
Example
header inspection
$ xxd -l 8 suspect.jpg00000000: 504b 0304 1400 0600 PK......extension .jpg · header PK\x03\x04 = ZIP/OOXML — mismatch
Cannot prove

A signature mismatch shows the name does not match the content. It does not show who renamed it, or when.

Record
  • Tool and version — HxD 2.5.0.0, TrID, ExifTool 13.59
  • Each file: its extension, its header bytes, and the type they indicate
  • Whether they agree, and the exact offset examined
Why it matters · admissibility: A header survives a rename, which is what makes it worth more than the extension. Recording the offset and bytes lets a second examiner reach the same conclusion without taking your word for the file type.
Metadata & embedded content extractionactiveexiftool · OLE / OOXML structure
Example
exiftool 13.59
Create Date : <timestamp>Modify Date : <timestamp>Author : <value>macro storage present: vbaProject.bin
Record
  • Tool and version, and the exact file examined with its path
  • Metadata fields recovered, quoted as they appear
  • Embedded objects or macro storage found, and where inside the file
  • The time zone the timestamps are expressed in
Why it matters · admissibility: Metadata is written by software, not by an oath — it is evidence of what a program recorded, which is why the field is quoted rather than summarised. Embedded macro storage is a fact about structure; what it did is interpretation.

Partition structure recovered and provenactiveMBR / GPT · prove the recovery
Example
partition table
$ mmls EVI-SRC01.E01002: 000 0000002048 0000411647 NTFS / exFAT# wiped table? recovered with TestDisk 7.2 (stable, never 7.3-WIP)recovery verified: volume mounts read-only, hash unchanged
Record
  • Tool and version used to read or recover the table
  • The partition layout found: scheme, offsets, sizes, types
  • If recovered: what was damaged, what was restored, and how the recovery was verified
  • That the image hash is unchanged after the work
Why it matters · admissibility: Recovering a partition table is an assertion about the disk's original layout, so it needs proof — a mounting volume and an unchanged image hash. Without them it is a claim, not a finding.
File system parsed — $MFT and deleted entriesactiveMFTECmd · Timeline Explorer
Example
MFTECmd
> MFTECmd.exe -f $MFT --csv out\<n> records · <n> flagged not-in-use# resident vs non-resident · ADS · $LogFile / $UsnJrnl
Record
  • Tool and version, input artifact and its full path in the image
  • Records parsed, and how many are marked not in use
  • For each artifact of interest: its MFT record number and timestamps
  • Whether data is resident or non-resident, and any alternate data streams
Why it matters · admissibility: The $MFT is the file system's own record, so citing a record number lets a second examiner go straight to the same entry. Deletion in NTFS clears an in-use flag rather than the data — which is why a “deleted” file can still be a finding.
File carvingactivePhotoRec / foremost
Example
carving
$ foremost -t all -i EVI-SRC01.dd -o carved/<n> files carved · first at offset <n>
Cannot prove

A carved file has no filename, no path and no file-system timestamps — carving recovers content, not context.

Record
  • Tool and version, and the image carved
  • Files recovered, their types, and the byte offsets they came from
  • Which carved items are complete and which are partial
Why it matters · admissibility: Carving finds content by signature alone, so the offset is the only address it has. Recording what carving cannot supply — name, path, timestamps — is what keeps the finding honest.

USB & removable-media historyactiveUSBSTOR · MountedDevices · setupapi.dev.log
Example
device history
SYSTEM\CurrentControlSet\Enum\USBSTOR\<device>\<serial>first connected: <timestamp> · last: <timestamp>MountedDevices → volume GUID · setupapi.dev.log → first install
Cannot prove

Device history shows a device was attached. It does not show who attached it, or that any file was copied to it.

Record
  • Full key path, the device serial, and the timestamps quoted as stored
  • The volume GUID and drive letter it mapped to
  • Which artifact each fact came from — they do not all say the same thing
Why it matters · admissibility: This is the artifact family the whole case ends on, so the key path and serial have to be exact. Attribution to a person is a separate question that needs a separate artifact — the registry records devices and accounts, not people.
Execution evidenceactivePrefetch · Amcache · ShimCache
Example
evidence of execution
/Windows/Prefetch/<NAME>-<HASH>.pfrun count <n> · first run <ts> · last run <ts>Amcache / ShimCache = presence, NOT proof of execution
Record
  • Artifact path, tool and version, and the values as parsed
  • Run count with first and last run times, where the artifact carries them
  • Which artifact proves execution and which only proves presence
Why it matters · admissibility: Prefetch evidences execution; ShimCache and Amcache evidence that a binary was present. Writing one as the other is the classic misreading, and it is the difference between a finding that survives and one that does not.
