Session 03

Data Representation, Hidden Information & File Examination

By the end of today you can say what a file really is, and find what is hidden inside it when no extension check ever would.

EVS-05 EVS-10 Case 03 office_floor3.jpg
Where this sits

Third of six. Sessions 1 and 2 established that a name is a label. Today is the next layer: the file is not what it says, and something is inside it that no name check will ever reach.

How this session works

Two threads, each finished before the next starts

The order is deliberate

EXIF → thumbnails → hidden data is one continuous thread about images, and invoice_batch.jpg is its hinge. Documents and executables are the second thread, and the binary you read is the one the document drops.

Objectives

By the end of this session you can

  1. Read the same bytes two ways and say why the number changed.
  2. Extract metadata, and state which timestamp you trust and why.
  3. Recover an image the file kept after the picture was edited.
  4. Detect a payload hidden in pixels, and a file appended to another file.
  5. Open a macro-enabled document as the archive it is, and find the macro.
  6. Read a binary's imports and say what it is able to do, without running it.
The claim

“The export list tells us what was taken.”

Twelve names. Nobody has looked inside any of them.
The claim on trial today

Twelve files were taken, of the twelve types the list names.

What the list is

A record of what the export tool was told to call things. It is not an observation of content, and it was never checked.

S3-01 · 10 min

The bytes do not say which way to read them

Do it now

Take 00 10 00 00. Write the little-endian value and the big-endian value. One of them is 4 096; say which, and how you knew.

Where this bites

Every offset, length and timestamp you read by hand for the rest of this diploma is stored in one order or the other. Guess wrong and the number is not slightly off — it is unrelated.

S3-06 · 12 min

What the file kept after the picture was edited

invoice_batch.jpg · extract the thumbnail
$ exiftool -b -ThumbnailImage invoice_batch.jpg > thumb.jpg
main image : 600x400, 14 kB
thumbnail : 160x107, 1 735 B
# written when the photo was made, not when it was edited
One command. The redaction never touched this copy.
Why this keeps happening

Editors that redraw pixels often leave the embedded preview alone, and so do many “save a copy” paths. Nobody intends it — which is exactly why it is worth checking every time.

S3-03 · part 1 of 33 min

A payload you cannot see

Do it now

Open both files. Look at them side by side and satisfy yourself that you cannot tell them apart. Then diff them and count the differing pixels.

How you write this one

190 pixels of receipt_scan.png differ from receipt_scan_clean.png, all in the blue channel, each by exactly 1. State the count and the channel — not what the payload says, which you have not read yet.

The rule that covers all four

A file ends where its format says it ends, not where the byte count does. Everything after that is somebody's choice.

S3-04 · 25 min

A document is an archive, and the macro is a file in it

quarterly_review.docm · unzip -l
$ unzip -l quarterly_review.docm
486 [Content_Types].xml
272 word/document.xml
1 536 word/vbaProject.bin
512 word/embeddings/oleObject1.bin
6 files, 3 532 B uncompressed
Rename it to .zip if you like. It was always one.
Two container formats, one artifact

OOXML on the outside — a ZIP of XML parts. OLE on the inside: vbaProject.bin begins d0 cf 11 e0, the compound-file signature. Older .doc files are OLE all the way down.

S3-05 · 25 min

What a binary tells you before you run it

report_viewer.exe · objdump -p
$ objdump -f report_viewer.exe
file format pei-x86-64
$ objdump -p report_viewer.exe | grep 'DLL Name'
DLL Name: KERNEL32.dll
DLL Name: msvcrt.dll
... GetSystemDirectoryA, MultiByteToWideChar
Real output from a benign binary compiled for this session.
Do it now

Pick three imports from the list and say, for each, one thing the binary is able to do. Then say the thing you cannot conclude from an import table.

What an import table cannot show

That a function is ever called, in what order, or on what condition. Imports are capability, not behaviour — and code can resolve functions at run time without declaring them here at all.

Independent practice

All twelve, by their bytes

  1. Read the first four bytes of every file in EVS-05.
  2. Tabulate: name · extension it claims · bytes · what those bytes say it is.
  3. Name the five that disagree. One of them will surprise you — predict it first.
  4. Name the two whose signature is correct and which still will not open.
  5. For one file of each kind, write the finding with its exact path.
Predict before you look

Write down what you expect policy_v2.docx to begin with, then check. The point of the exercise is the gap between those two moments.

The document from the case itself

Takeaways

Five things to leave with

1

Byte order is a convention, not a property of the bytes. Know it before you read a number.

2

A valid signature says how a file starts. It says nothing about whether it is complete.

3

Editing a picture is not editing the file. Check what the container kept.

4

A file ends where its format says it ends. Everything after that was a decision.

5

Imports tell you capability. They never tell you behaviour.

And the one this session is built around

Three dates, nine days apart, and none of them answers the question you were asked. “Cannot be determined” with the best indicator named is the professional answer.
