## Every number on the page was measured

Nothing on this page is quoted from a specification without also being read out of a disk. The four
images were generated by `scripts/make_evs07.py`, and a separate 37-assertion pass read them back.

**Slack — the FAT16 volume, 4 096-byte clusters (`-s 8`, so the arithmetic is exact, not "whatever
mkfs decided today"):**

| File | Size | Allocated | Slack |
|---|--:|--:|--:|
| `TINY.TXT` | 1 | 4 096 | **4 095** |
| `NOTE.TXT` | 100 | 4 096 | **3 996** |
| `EXACT.BIN` | 4 096 | 4 096 | **0** |
| `OVER.BIN` | 4 097 | 8 192 | **4 095** |
| `REPORT.PDF` | 10 000 | 12 288 | **2 288** |
| | **18 294** | **32 768** | **14 474** |

Five files. **14 474 bytes of a 20 MiB volume are allocated to files that are not using them** —
and `OVER.BIN` is the one that lands: one byte past a cluster boundary costs a whole cluster.

**Slack carries data, proved by running it.** `MEMO.TXT`, 20 bytes, cluster 10, offset `0x13000`.
The remaining **4 076 bytes** of that cluster return a document nobody listed. `strings` on the
cluster returns **one line, not two** — the memo runs straight into the previous document with no
separator on the disk at all. The only thing that says where the file ends is the size field in the
directory entry, and it says 20.

**MBR — written byte by byte, not by `fdisk`:**

```
disk signature   C4 19 7F A3          at 0x1B8
entry 1          type 0x06  LBA 2048   40960 sectors   FAT16 20 MiB
entry 2          type 0x0C  LBA 45056  81920 sectors   FAT32 40 MiB
entry 3, 4       16 zero bytes each
                 55 AA                 at 0x1FE
```

`fdisk` and `sfdisk` were both unavailable in the build environment, so the table was assembled in
Python — which turned out to be the better demonstration anyway: **the students see the sixteen
bytes, not a tool's summary of them.**

**GPT:** protective MBR type `0xEE` · `EFI PART` at LBA 1 · header 92 bytes · header CRC32
`0x26AFC734` and entry-array CRC32 `0x6856CA25`, **both recomputed and matched during
verification** · 128 entries × 128 bytes · backup header at LBA **131 071**.

## Case 04 — the strongest evidence work on the page

`EVS-07-wiped.dd` is `EVS-07-mbr.dd` with LBA 0 zeroed and nothing else touched: **512 of
67 108 864 bytes, 0.0008% of the disk**, and it will not mount.

A naive boot-sector scan returns **three** hits: LBA 2048, 45056 and **45062**. Three hits, two
partitions. The third is not a partition — the FAT32 volume at 45056 records `BPB_BkBootSec` = 6 at
offset 50 of its own boot sector, so 45 056 + 6 = **45 062 is that volume's own backup boot
sector**. Discard it, rebuild the table from the two survivors, and the result is **byte-identical**
to the original:

```
sha256(bytes 446..510) = e541ef6f624eb09775c4b21f70bc08e85188d26788febf4ffd9e2c758cde5cab
```

**The wrong answer that still works is the lesson.** A table built from all three candidates also
mounts. `ON YOUR OWN` is four recovery claims to sign or refuse, and the report stage asks for the
**discarded candidate** in writing — because an IT recovery writes a table that works and stops,
while a forensic recovery shows why one candidate was excluded.

## What changed outside this page

**`scripts/make_evs07.py` is now deterministic.** It was not, and the manifest would have been a
lie the first time anyone regenerated the set. Five separate sources of drift, all pinned:

| Source | Fix |
|---|---|
| `mkfs.fat` takes the FAT volume serial from the clock | `-i A1B2C3D4` / `-i B2C3D4E5` |
| `mcopy` stamps directory entries with the current time | `-m`, plus a fixed mtime on every payload file |
| FAT stores **local** time, so the timezone is in the output | `TZ=UTC` pinned inside `build()` |
| `mkfs.fat` also stamps the **volume-label** entry | `pin_label_time()` parses the BPB to find it |
| `sgdisk` invents three random GUIDs, and both CRC32 fields cover them | `-u 1: -u 2: -U` fixed |

Two builds to different paths are now byte-identical across all four images. Before the fix they
differed in as little as **two bytes** — which is exactly the amount that makes a manifest worthless.

**The terminology gate was wrong, and eight pages were clean by it and were not.** See `D132`.

## Known trade-off, not a defect

The SIMSCREEN stage has a 420 px floor so the frame does not jump between steps. On a deck of small
terminal windows — like `ss-t12` here — that leaves visible space above and below the window. The
fix is to size the stage from the deck's own tallest step, which means changing how every SIMSCREEN
on every page is laid out and re-checking each cursor hotspot. **Not done inside a page build.**
